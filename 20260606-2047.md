Stage 6 uses **inline `cl_fix_mult()`** and stage 7 uses **inline `cl_fix_add()`**, both inside the two-process combinatorial process -- identical to what PSI-FIX does and how the CIC accumulator works in `olo_fix_cic_dec_tdm`.

The reason `olo_fix_mult` (entity) and `olo_fix_madd` (entity) are not used:

- Stage 7 is a **running accumulator**: it conditionally resets to zero based on the `First` signal, then adds `MultOut_6` to the stored `r.Accu_7`. This conditional-reset logic is tightly coupled to the pipeline control signals inside the record -- it can't be cleanly separated into an external entity with fixed latency.
- `olo_fix_madd` is designed for multiply-accumulate chains where a new result is computed per clock. Here the accumulator runs across `MaxTaps_g * Channels_g` consecutive clock cycles before the result is used.

So in the combinatorial process:

```vhdl
-- Stage 6: multiply
v.MultOut_6 := cl_fix_mult(r.MultInTap_5, InFmt_c,
                            r.MultInCoef_5, CoefFmt_c,
                            MultFmt_c, Trunc_s, None_s);

-- Stage 7: accumulate (reset on First tap)
if r.First(6) = '1' then
    AccuIn_v := (others => '0');
else
    AccuIn_v := r.Accu_7;
end if;
v.Accu_7 := cl_fix_add(r.MultOut_6, MultFmt_c,
                        AccuIn_v, AccuFmt_c,
                        AccuFmt_c, Trunc_s, None_s);
```

Then `olo_fix_resize` (entity) handles the final rounding + saturation from `AccuFmt` to `OutFmt`, triggered by `Last(7) and CalcOn(7)`.
