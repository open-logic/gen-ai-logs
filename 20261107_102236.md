**How it works** (mirrors `olo_fix_cic_dec_par_tdm`; same generics and `Cfg_*` ports):
- **Input side (TDM):** the comb stages are shared by all channels and work at full precision, so nothing is rounded there. The delay lines are `olo_base_delay`.
- **Middle:** in configurable mode there is one dynamic left shift, then TDM to parallel conversion (`olo_base_wconv_n2xn`), then zero-stuffing.
- **Output side, per channel:** the integrators, then a fixed shift (wiring only), then a resize, or a resize plus gain-correction multiply.
- **Shift trick:** the integrators are sized for `Ratio_g`. For a smaller configured ratio, the data is shifted left by `MaxShift - Cfg_Shift` *before* the integrators. That gives the same result, bit for bit, as shifting right afterwards, but needs one shifter in total instead of one per channel. `Cfg_Shift` and `Cfg_GainCorr` mean the same as in the decimator, using the interpolator gain (R*M)^N/R.
- **`In_Ready`:** only the last sample of a TDM frame can be held back, until R cycles have passed since the previous frame. It's a single small counter, so there is no enable/disable generic. A mutation test confirmed the timing is tight: shortening it by one cycle makes the testbench fail.
- **`In_Last`:** used only for a check in simulation, as in `olo_fix_cic_dec_tdm`.

**Things to be aware of:**
- **`olo_base_rate_limit` needs a FIFO in front of it.** It applies backpressure, which the CIC can't accept. I documented the chain as CIC -> `olo_base_fifo_sync` (depth R) -> `olo_base_rate_limit` in SMOOTH mode.
- **One gain-correction multiplier per channel.** This can't be avoided with parallel full-rate outputs. Doing the correction before the integrators would let rounding errors pile up.
- **`Cfg_Shift` uses integer arithmetic in VHDL.** `MaxShift - Cfg_Shift` is plain integer math on a configuration value, not on the data path. I think that's within the spirit of the `olo_fix` rule, but you may want to check it.
- **en_cl_fix inconsistency.** `cl_fix_from_integer()` returns a `WideFix` object instead of raw data for wide formats. The model works around it the same way the decimator model does.

Short answer: BLOCK mode can't do it. SMOOTH mode could, but I recommend keeping the current Ready logic.

**On reset-only configuration:** yes, that already applies. The `Cfg_*` ports may only change while `Rst` is asserted, the same as for the decimators, and the doc says so. My Ready logic already relies on this (it reads `Cfg_Ratio` as if it were constant).

**What the CIC needs:** every TDM frame becomes R parallel output beats on R consecutive cycles. So the last samples of consecutive frames must be at least **R** cycles apart, not R x Channels. With R x Channels, throughput would drop by a factor of `Channels_g`.

**What a brute-force model of `olo_base_rate_limit` showed:** I simulated it cycle by cycle against that requirement, for R=2..16, every channel count up to R, and random input gaps.

| Mode / setting | Result |
| --- | --- |
| BLOCK, Period=R, MaxSamples=Ch | Fails (frame ends as close as 1 cycle) |
| BLOCK, Period=R*Ch, MaxSamples=Ch | Fails |
| SMOOTH, Period=R, MaxSamples=Ch | Spacing was always at least R |

BLOCK fails because its windows are fixed in time and don't line up with TDM frames. A frame can be split across two windows, and the window limit then lets the next frame through too early. For example, with Ch=2 and R=4, samples can be accepted at cycles 2 and 3, then 4 and 5. Frame ends would be 2 cycles apart where 4 are needed.

**Why I'd still keep the current logic:**
- **It costs about the same or less.** The current logic is one down-counter, the channel counter and one register. SMOOTH needs its credit counter plus add/subtract and, with runtime configuration, three config registers including a subtraction.
- **SMOOTH needs special handling when `Channels_g > R`.** It requires MaxSamples <= Period. With a runtime ratio, the configured R can drop below `Channels_g` even when `Ratio_g` is larger, which would trip its runtime assertion.
- **The guarantee would be indirect.** The CIC's correctness would depend on how `olo_base_rate_limit` spaces samples internally, which its doc doesn't promise. If that block changes, the CIC breaks without any error. Today the internal assertion plus the mutation test cover the current logic directly.
- **The current logic only holds back what it must.** It never delays the other channels' samples; SMOOTH spaces every sample by R/Ch cycles. Throughput is the same either way.

I haven't changed anything. If you'd rather have the reuse anyway, I can switch to SMOOTH mode with a bypass for `Channels_g >= R`.

Yes, the option exists. It's the same in all three CICs (`olo_fix_cic_dec_tdm`, `olo_fix_cic_dec_par_tdm` and `olo_fix_cic_intp_tdm_par`), and it's controlled by the generic `GainCorrCoefFmt_g`.

**What the user controls:**

| `GainCorrCoefFmt_g` | Result |
| --- | --- |
| `"NONE"` | No multiplier. The gain is only corrected by the bit shift, so the overall gain ends up between 0.5 and 1.0. |
| A format such as `"(0,1,16)"` (the default) | A multiplier is built and corrects the gain to exactly 1.0. The format sets the coefficient precision and must be unsigned with one integer bit. |

**With a fixed ratio (`FixedRatio_g = true`), everything is calculated automatically:**
- **Shift:** computed at elaboration from `Ratio_g`, `DiffDelay_g` and `Order_g`. For a fixed shift it's pure wiring.
- **Coefficient:** computed at elaboration as `FixedGc_c = 2^Shift / Gain`, quantized to `GainCorrCoefFmt_g`. The multiplier uses this constant (`GcCoef_0 <= FixedGc_c when FixedRatio_g else r.GcCoef`).
- **Config ports:** `Cfg_Shift`, `Cfg_GainCorr` and `Cfg_Ratio` are ignored and can be left unconnected.

So in fixed-ratio mode the only decision left to the user is whether to correct the gain to exactly 1.0, which they make by choosing `"NONE"` or a coefficient format.

**With a configurable ratio**, the user supplies `Cfg_Shift` and `Cfg_GainCorr` for the configured ratio, using the formulas in the docs. The on/off decision is still made at compile time by `GainCorrCoefFmt_g`.

**Two weak spots I noticed:**
1. **Power-of-two gains still get a multiplier.** In fixed-ratio mode the correction factor is then exactly 1.0, so the multiplier does nothing, but it's still built unless the user sets `"NONE"` by hand. ## Assistant <sup>11/7/2026, 11:14:08 AM</sup>

Mostly correct. The comb next to the rate change can be merged into a sample and hold, but it takes the first integrator with it. The VHDL doesn't use this today; it implements the textbook structure with `Order_g` combs, zero-stuffing and `Order_g` integrators.

**Why it works (M = 1):** in output-rate terms, the last comb is `1 - z^-R`. Zero-stuffing followed by the first integrator `1/(1 - z^-1)` gives:

```
(1 - z^-R) / (1 - z^-1) = 1 + z^-1 + ... + z^-(R-1)
```

That's a boxcar of length R applied to a zero-stuffed signal, which simply repeats each input sample R times. So one comb plus zero-stuffing plus one integrator becomes one comb less, a sample and hold, and one integrator less.

**For M > 1 it needs a small change:** `(1 - z^-MR)/(1 - z^-1)` isn't a plain hold. But a comb with delay M factors as `(1 - z^-1) * (1 + z^-1 + ... + z^-(M-1))` at the input rate. The difference part merges into the hold as above, and what's left is a short running sum at the input rate. For the usual M = 2 that's just `x[n] + x[n-1]`: one adder and one delay line, the same cost as the comb it replaces. So the trick works for any M. Only for M = 1 is the leftover stage nothing at all.

**It produces exactly the same output, bit for bit.** All the stages are linear integer operations that wrap at the register width, and both versions start from zero state after reset. So the Python model wouldn't need to change; only the VHDL structure would.

**What it would save:**
- **Per channel, at the full output rate (the expensive part):** one integrator, meaning an accumulator register and adder of the full accumulator width, plus one pipeline stage. This scales with `Channels_g`.
- **On the TDM side:** one comb, meaning a subtractor and an `olo_base_delay` line, for M = 1. For M > 1 the comb becomes the running-sum stage instead.
- **Zero-stuffing logic:** it gets slightly simpler, because it holds the value instead of inserting zeros.

**Cost:** some extra code structure. The hold replaces the zero-stuffing, there's one stage fewer of each kind, and a separate path is needed for M > 1. `Order_g >= 2` still leaves at least one comb and one integrator, so nothing degenerate happens.

I'd recommend doing it, since the per-channel integrator at the full rate is the main cost of this entity. Shall I implement it in `olo_fix_cic_intp_tdm_par`, for both M = 1 and M > 1, with the doc and figure updated?

## Assistant <sup>11/7/2026, 11:20:09 AM</sup>

The optimization is in both the VHDL and the Python model. It produces exactly the same output, bit for bit, as a classical CIC interpolator, and saves one full-rate integrator per channel. For `DiffDelay_g = 1` it also saves one comb.

**Structure (VHDL and model):**
- **Stages:** `Order_g-1` combs and `Order_g-1` integrators instead of `Order_g` of each.
- **Running sum:** replaces the last comb, on the TDM side. For `DiffDelay_g = 1` it passes the data straight through. For M > 1 it adds M-1 earlier samples of the same channel, using a chain of `olo_base_delay` taps (depth `Channels_g` each) and one register stage.
- **Sample and hold:** one `olo_fix_sample_hold` per channel replaces the zero-stuffing data register. My R-cycle counter still enables the integrators, because `olo_fix_sample_hold` keeps `Out_Valid` high permanently once it has sampled. The Ready logic is unchanged.
- **Python model:** `olo_fix_cic_intp` is structured the same way and uses the `olo_fix_sample_hold` model for the hold. The class docstring explains the factorization.

**Verification:**
- **Exact comparison:** a new unit test compares the model against a classical CIC (N combs, zero-stuffing, N integrators) computed in plain integers. Outputs are identical for M = 1, 2 and 3.
- **Python:** 100% statement coverage, and all 322 fix model tests pass.
- **Simulation:** I added `DiffDelay_g = 3` configurations to exercise the multi-tap running sum. All 196 CIC tests pass in NVC (88 for the interpolator, the rest for both decimators). GHDL also passed the 88 interpolator tests.
- **Lint:** VSG and markdownlint are clean.

**Docs:** the architecture figure now shows `Order_g = 3`, the running sum (green for `DiffDelay_g = 2`, red bypass for 1) and `olo_fix_sample_hold` per channel. The architecture section explains the factorization and why the result is identical.

**One limitation:** I found a bug in the `olo_fix_sample_hold` Python model. For wide formats (more than 53 bits) it re-quantizes the stored raw integer with `cl_fix_from_real` and returns wrong values. To avoid silently wrong output, the CIC model now raises a `ValueError` if the format before the integrators is wide. That only happens with inputs of about 45 bits or more. Wide integrators still work, and the VHDL has no such limitation. I didn't change `olo_fix_sample_hold` itself; fixing its model (no re-quantization of already-quantized wide values) would lift the restriction. Want me to do that?

## Assistant <sup>11/7/2026, 11:35:43 AM</sup>

It's feasible, but I'd recommend against it for the CIC. Making `olo_fix_mov_avg` TDM-capable would still be a reasonable feature in its own right.

**Feasibility:**
- **VHDL:** with `GainCorrType_g = "NONE"` and `OutFmt_g` equal to its internal sum format, `olo_fix_mov_avg` is an exact running sum. Its integer growth of `log2ceil(Taps)` matches my hold format. Making it TDM-capable is straightforward:
  - a `Channels_g` generic (default 1),
  - the delay line depth becomes `Taps_g * Channels_g`,
  - the single accumulator register `Sum_2` becomes per-channel state: the register plus an `olo_base_delay` of `Channels_g-1` in the feedback loop,
  - optional `In_Last`/`Out_Last` handling.
- **Python model:** no change needed. As with the CIC, multiple channels are modelled as one instance per channel.

**Why it's worse for the CIC:** `olo_fix_mov_avg` computes the sum recursively (difference with a T-tap delay, then accumulate). That pays off for long windows, but the CIC's window is only M = `DiffDelay_g` wide, and M is practically always 1 or 2. psi_fix even restricted it to that range.

| Running sum over M | Current (direct taps) | `olo_fix_mov_avg` (recursive) |
| --- | --- | --- |
| Delay memory | (M-1) x `Channels_g` | M x `Channels_g` + (`Channels_g`-1) for the accumulator loop |
| Adders | M-1 | 2 (subtract plus accumulate) |
| M = 1 | nothing (pass-through) | needs a bypass anyway |
| M = 2 | 1 delay of `Channels_g` + 1 adder | about 3x the delay memory + 2 adders |

The recursive version only saves adders for M >= 4 and always needs more delay memory. For the cases that occur in practice it would cost resources.
