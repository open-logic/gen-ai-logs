## Assistant <sup>8/17/2026, 9:43:08 PM</sup>

Right — and that's intentional, not an oversight. The key is that **each lane holds a *full copy* of the entire coefficient set**, not a per-lane slice. The lanes are differentiated by the *read address*, not by their init.

## How it works

Every lane's [olo_fix_coef_storage](src/fix/vhdl/olo_fix_coef_storage.vhd) gets:
- `Depth_g => CoefMemDepth_c` = `2**log2Ceil(Multipliers_g * TapsPerStage_c)` — big enough to hold the whole set (plus padding).
- `Init_g => CoefInit_g` — the **complete** comma-separated list. `olo_fix_coef_storage` parses it with `fromString`, writing coef[0..Taps-1] into addresses 0..Taps-1 and leaving the rest at 0.

So after init, **all M copies are byte-identical**, each an image of the full array indexed by *global* tap number.

The lanes diverge only at the read port ([lines 556-557](src/fix/vhdl/olo_fix_fir_dec_semi_chtdm.vhd#L556-L557)):

```vhdl
CoefRdAddr <= to_unsigned(i * TapsPerStage_c, ...) + resize(unsigned(r.CoefRdAddr(i + 3)), ...);
```

Lane `i` in cycle `c` reads global tap `i*TapsPerStage_c + c`. Because lane `i`'s data-RAM in the chain is delayed by `i*TapsPerStage_c` samples, that lane multiplies coef[`i*TPS+c`] with x[n − (`i*TPS+c`)] — the correct pairing. Any global address ≥ Taps (padding when Taps isn't divisible by Multipliers) reads a 0 coefficient → 0 contribution.

Writes and readback fall out for free: `Cfg_Addr` is the same global index, so `Coef_WrEna`/`Coef_WrData` are **broadcast to all copies** (keeping them identical), and readback is just taken from lane 0.

## The trade-off

The alternative (the psi_fix template's approach) is to give each lane only *its* contiguous block of `TapsPerStage` coefficients. That's less memory but requires:
- splitting the `CoefInit_g` string into per-lane sub-lists at elaboration (there's no real→string helper in the olo packages, so this is genuinely awkward), and
- routing coef writes to the right lane and muxing readback back out with the read-latency delay.

I chose the full-copy version because it makes init/write/readback trivial and robust, at the cost of replicating the (small) coefficient memory M times. For coefficient storage that's cheap; I flagged the replication in the doc's Architecture section. If coefficient ROM/RAM footprint ever became a concern for a large-M, large-Taps instance, the sliced-block scheme would be the optimization — but it buys memory at a real complexity cost.
