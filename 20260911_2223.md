## Assistant <sup>9/11/2026, 10:33:32 PM</sup>

The normalization is a leading-one alignment, so the normalized value always lands in **[1, 2)**, never (1, 2]. An input of exactly `2^k` (e.g. 1.0, 0.5, or the most negative value of a signed input) normalizes to exactly 1.0, and the approximation therefore has to deliver `1/1.0 = 1.0`. Shifting such an input to 2.0 instead would itself need a special case (the mantissa would have to hold the value 1, which needs an integer bit again), so it does not save anything.

Two things worth knowing before you decide:

- Scaling the table to `0.5/(1+m)` so the result fits `(0,0,P)` does **not** save a bit: the result then only occupies the range (0.25, 0.5] of the format, so `(0,0,P+1)` is needed for the same relative accuracy — the same width as `(0,1,P)`. It is a wash, so `(0,1,P)` is the cleaner of the two.
- The real trade is against PSI's `(0,0,P)`: that is one bit narrower in the output barrel shifter, but `1/1.0` saturates to `1-1LSB` (one LSB relative error at exactly the point where the result should be trivially exact).

Both questions answered, and I applied the P=20 change.

## P=20: yes — and it doesn't need the relaxation

Applied: **1024 × 35 = 35 840 bits** (was 1024 × 37 = 37 888), error **0.898 LSB**, exhaustively verified over all 2²² input codes, `1/1.0` still exact. That is below 36 kbit, so the table now fits a single BRAM36 (1024×36) instead of spilling into a second block. End-to-end relative error is 2^-19.57, still inside the documented `< 2^-19`.

The interesting detail: at 1024 points the entry width cannot go below 35 at all — w=34 jumps to 1.048 LSB. So **35 840 bits is the hard floor for P=20 whether the budget is 0.9 or 1.0 LSB**; the ±1 LSB relaxation buys nothing extra there. I picked w=35 over w=36 because exhaustively they are equally accurate (0.8976 vs 0.8982), so the extra bit is wasted.

## Generally: it saves bits, but no FPGA resources

The point counts are already at their floor — the tangent error alone (`h²/4`) forces 32/128/512/1024 points for P=10/14/18/20, and no error relaxation changes that. Only the entry width can shrink:

| P | current | min at <1.0 LSB | saving | block RAM change |
| --- | --- | --- | --- | --- |
| 10 | 32×22 = 704 b (0.68 LSB) | 32×18 = 576 b (0.91) | -18% | none, it is LUT ROM |
| 14 | 128×29 = 3712 b (0.77) | 128×25 = 3200 b (0.94) | -14% | none, it is LUT ROM |
| 18 | 512×36 = 18432 b (0.76) | 512×32 = 16384 b (0.94) | -11% | none, already exactly 1 BRAM18 |
| 20 | 1024×37 (0.82) | **1024×35 = 35840 b (0.90)** | -5% | **2 → 1 BRAM36** ✅ applied |

(The P=10/14/18 figures are exhaustive, not sampled — their input spaces are ≤ 2²⁰.)

So the relaxation saves 11-18% of raw table bits on the three smaller precisions, but **zero actual FPGA resources**: those tables are either LUT-ROM-tiny or already fit one block exactly. That is why I left them alone — the accuracy would drop from ~0.77 to ~0.94 LSB and buy nothing. It would also leave the documented `< 2^-(P-1)` relative bound with almost no margin instead of ~25%. Say the word if you want the LUT-ROM savings anyway.

Side benefit: the generated package's shared entry padding dropped from 40 to 36 bits, since 35 is now the widest table.
